# Рекомендации по производству

## Модель процесса

`stask:worker` — команда бегства и выхода. Он создаёт запланированные задачи, последовательно обрабатывает готовые строки в очереди и выходит из них. Для постоянного обслуживания запускайте планировщик Laravel каждую минуту.

```cron
* * * * * cd /var/www/example/core && /usr/bin/flock -n /run/lock/example-stask.lock /usr/bin/php artisan schedule:run >> /var/log/example-scheduler.log 2>&1
```

`flock` — Охрана инфраструктуры от перекрытия. Выберите путь записанного блокировки и проверьте, не блокирует ли одна длинная задача важные, не связанные между собой задачи планировщика. Альтернативой является отдельный системный блок/таймер с политикой `RefuseManualStart`/locking.

## Владелец и права

Пользователь веба и пользователь CLI должны обладать совместимыми правами на:

- `core/storage/stask`;
- Кэш/хранилище Laravel;
- каталог загрузки результатов;
- ресурсы приложений, которые изменяет работник.

Не запускайте cron из root без необходимости: файлы прогресса/кэша, созданные root, часто ломают процесс менеджера.

## Тайм-аут

Путь запуска менеджера может вызывать `set_time_limit(0)`, и команда CLI не устанавливает тайм-аут для каждой задачи. Тайм-ауты должны быть в работе:

- Тайм-аут HTTP-соединения/чтения;
- Тайм-аут выписки базы;
- максимальное количество предметов/партий на задачу;
- крайний срок в метаданных;
- Изящные контрольные пункты отмены.

Разбивайте длительные работы на идемпотентные части. Одна монолитная задача блокирует следующий график с тем же идентификатором работника.

## Соревновательность

Текущий CLI выбирает строки в очереди без атомарного запроса претензий/`FOR UPDATE SKIP LOCKED`. Следовательно:

- держать один `stask:worker` на одну установку;
- Использовать внешний замок перекрытия;
- сделать действие идемпотентным;
- для критических интеграций использовать ключ идемпотентности на уровне домена;
- Не путайте дублированный поиск с гарантией транзакции.

Если требуется совместность, сначала составьте договор претензии/аренды; Просто увеличение числа процессов опасно.

## Перепробуйте и отступайте

`attempts/max_attempts` не запускают повторные попытки в одиночку. Политика производства должна определять:

- повторяемые классы исключений/коды статуса;
- максимальное количество попыток;
- `start_at` для отступления;
- обзор «мертвого письма»/руководства;
- поведение дублирования/идемпотентности;
- оповещение после последней ошибки.

## Мониторинг

Минимальные проверки:

- планировщик пульса/последний успешный запуск;
- количество поставленных в очередь задач и возраст самых старых;
- возраст выполнения задач;
- процент отказов;
- `storage/stask` для письма;
- прогресс/результаты использования диска;
- работников, отсутствующих в классе/неактивных работниках;
- `s_supervisor_states.last_seen_at` и свежесть сердцебиения;
- идентичность PID демона.

Встроенная вкладка Статистика не заменяет APM: duration/memory/common-errors частичными заполнями.

## Бревна

Существует три разных источника:

1. `s_tasks.message/meta/result` — постоянный аудит/состояние.
2. `storage/stask/{id}.log` — живой прогресс только с приложением.
3. журналы приложений через Laravel `Log` — исключения, обнаружение, предупреждения о запуске.

Определите удержание индивидуально. `cleanOldTasks()` удаляет только старые готовые строки базы данных; Прогресс `.log`, неудачные задания и состояние супервайзера не очищаются.

## Удержание

Пример политики, которую можно реализовать на уровне операций:

- выполненные задачи: 30–90 дней;
- невыполненные задачи: дольше или до рассмотрения инцидента;
- журналы прогресса: 7–30 дней после финального задания;
- загрузка/результаты: для бизнеса/юридической политики;
- состояние супервайзера: одна реальная строка на клавишу; Ряды сирот — после проверки инвентаря.

Не удаляйте прогресс активной задачи. Проверьте окончательный статус и подайте заявку на владение перед уборкой.

## Супервайзер/системный директор

sTask Supervisor — это адаптер жизненного цикла на уровне приложения, а не полная замена systemd/supervisor. Если процесс перезапускается systemd и адаптер sTask одновременно, согласитесь с одним владельцем, иначе возможны циклы перезапуска.

Рекомендуемые роли:

- systemd обеспечивает загрузку, пользовательское ограничение, ограничения ресурсов и перезагрузку после сбоя;
- Рабочий адаптер считывает здоровье/сердцебиение и возвращает диагностическое состояние;
- только один из них выполняет перезагрузку, либо оба имеют общий контракт на backoff/lock.

## Развертывание

Безопасная последовательность:

1. прекратить создание новых рабочих мест или дождаться завершения критически важных;
2. `composer install` с замком;
3. `php artisan migrate --force` после проверки резервного копирования и миграции;
4. `package:discover`/autoload rebuild;
5. `stask:publish`;
6. `cache:clear-full`;
7. обновить реестр работников после комплексного развертывания;
8. дымовой `stask:worker`;
9. Проверьте интерфейс менеджера и планировщик.

Не запускайте очистку реестра во время развертывания, когда классы временно отсутствуют.

## Безопасность

- разрешение `stask` только оперативных ролях;
- `run_artisan` отдельно для ArtisanWorker;
- белый список/чёрный список опасных командований;
- CSRF для POST;
- секреты, не входящие в мета/результат/сообщение/прогресс;
- загрузки в непубличном хранилище;
- работники проверяют ввод и авторизацию, даже если это только менеджер маршрутов;
- сервисная учетная запись с минимальными правами файловой системы/базы данных.
