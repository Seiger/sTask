# Диагностика

Начните с доказательств: ссылка на пакет, маршруты, миграции, планировщик, строка базы данных, файл прогресса, журнал приложений. Не заканчивайте только значком UI.

## sTask не виден в модуле документации

1. Проверьте физический артефакт:

   ```bash
   test -f core/vendor/seiger/stask/docs/uk/README.md
   ```

2. Проверьте источник замка/источника:

   ```bash
   cd core
   composer show seiger/stask --all
   ```

3. Убедитесь, что у dDocs есть `scan_vendor_packages = 1`.
4. Очистить кэш индекса/приложений.
5. Проверьте метаданные упаковки в `lang/{locale}/global.php`: `module_title`, `module_description`, `module_icon`.

dDocs автоматически сканирует посылки `seiger/*`. Не добавляйте root vendor в `extra_docs_roots`: настроенный корень проекта может стать записаным в просмотрщике.

Если документация в Git репозитории, а `core/vendor` нет, проблема в Composer lock/dist/deploy, а не в индексе Markdown.

## dDocs вылетает в индексацию

Проверьте трассировки стека в пакете документации третьей стороны. Файл псевдонима, провайдер сервиса или кэш могут вылететь до того, как исходный код sTask будет прочитан. Это отдельный дефектный dDocs/среда; Документация sTask не может исправить bootstrap другого человека.

## Модуль sTask не виден

- `composer show seiger/stask`;
- провайдер присутствует в Package Discovery;
- разрешение `stask` назначенной роли;
- миграции прошли;
- кэш менеджера очищен;
- регистрация модуля/плагинов выполняется установщиком Evolution CMS.

У провайдера есть метод регистрации менеджера, но фактическая запись модуля также может управляться установщиком/плагином пакета Evolution. Проверьте запись модуля базы данных и обнаружение пакетов, а не ручной вызов защищённого метода.

## Модуль без стилей и JavaScript

```bash
cd core
php artisan stask:publish
php artisan cache:clear-full
```

В сети браузера проверьте `stask-module.css`, `stask-module.js`, `stask.min.css`. Если развертывание использует файловую систему выпуска только для чтения, ресурсы должны быть опубликованы во время сборки.

## `stask:worker` не начнём

```bash
php -v
php artisan list | grep stask
php artisan route:list --path=stask
```

Пакет требует PHP 8.4. Проверьте, используют ли CLI и FPM одинаковые версии, `.env`, расширения и разрешения.

## Задача поставлена в очередь и не выполнена

Посмотрите:

```sql
SELECT id, identifier, action, status, start_at, created_at
FROM s_tasks
WHERE status IN (10, 30, 50)
ORDER BY id;
```

- cron фактически выполняется;
- `start_at` не в будущем;
- рабочий актив;
- класс существует и реализует `TaskInterface`;
- журнал приложения не содержит исключения для разрешения;
- нет внешнего замка, который был бы постоянно занят.

## Расписание не создаёт задачи

- `settings.schedule.enabled = true`;
- тип не `manual`;
- Бетонщик имеет `taskMake()`;
- нет неполной задачи этого идентификатора;
- дата-время один раз в будущем;
- еженедельный выпуск имеет `days`;
- Обычное окно действует и не на ночь;
- `stask:worker` проходит каждую минуту.

## Работник не появляется

```bash
composer dump-autoload
php artisan package:discover
```

Затем обновите реестр. Класс должен быть конкретным и находиться в карте классов Composer. Класс PSR-4, который Composer не оптимизировал в classmap, может не быть обнаружен в текущей реализации обнаружения в авторитативном/оптимизированном дампе.

Проверьте `config/excluded_namespaces.php`: большие пространства имён фреймворков намеренно опущены.

## `WorkerClassNotFound` / `WorkerInvalidInterface`

- название класса в `s_workers.class` правильно;
- автозагрузка обновлена;
- класс не абстрактный;
- класс реализует `TaskInterface`;
- конструктор не вылетает из-за зависимости от базы данных и настроек.

Не нажимайте «очистить» во время частичного развертывания: запись может быть удалена, пока класс временно недоступен.

## Живой прогресс 404

404 означает `storage/stask/{id}.log` не найден. Задача всё ещё может быть поставлена в очередь или запись может тихо провалиться.

```bash
ls -la core/storage/stask
```

Сравните пользователей/группу для FPM и Cron. См. статус/сообщение базы данных и журнал приложений.

## Прогресс заморожен, задача завершена

Файл прогресса только для добавления и не является источником достоверности для итогового статуса базы данных. Живой наблюдатель останавливается у терминальной линии на последней линии. Если пользователь завершил базу данных, но не вызвал `markFinished()` или не записал финальный снимок, интерфейс обновится после обновления Livewire, но файл может оставаться в работе.

## Аварийная остановка не остановила процесс

Это ожидаемый предел: действие переводит запись базы данных только в состояние failed. Найдите процесс с помощью инфраструктурной телеметрии, остановите его как обычно, проверьте побочные эффекты и запустите новую задачу.

## Цикл перезапуска супервайзера

- Стартап Грейс слишком мал;
- инспекция не распознаёт запуск;
- тайм-аут сердечного ритма короче реальной частоты;
- изменение отпечатков пальцев при каждом проходе с помощью временной метки/случайного текста;
- процесс также перезапустит systemd;
- Старт/рестарт не отсоединяется.

Отпечаток пальца должен быть стабилен для того же диагноза.

## Государство супервайзера растёт

```sql
SELECT worker_id, identifier, supervisor_key, COUNT(*)
FROM s_supervisor_states
GROUP BY worker_id, identifier, supervisor_key;
```

Уникальная `key_hash` предотвращает рост для той же пары, но новый рабочий идентификатор или ключ переменной создаёт новую строку. Исправьте стабильность ключей для очистки.

## Статистика показывает ноль длительности/памяти

Текущая реализация агрегации возвращает заполнительный ноль для этих метрик. Это не означает нулевое потребление. Используйте длительность задачи в журналах и внешнем APM.

## ArtisanWorker блокирует команду

Проверьте `config/artisan_security.php`:

- опасные команды запрещены;
- требуется подтверждение `confirm=true`;
- белый список, если не пустой, допускает только перечисленные узоры;
- блокирует дополнительные команды в чёрный список;
- Требуется разрешение `run_artisan`.

Не отключайте проверки безопасности в производстве.
