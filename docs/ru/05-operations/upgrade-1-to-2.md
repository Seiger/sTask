# Переход с sTask 1.x на 2.x

Это чек-лист, основанный на доказательствах, а не автоматический апгрейд. В репозитории нет полного машиночитаемого контракта на миграцию для всех сторонних 1.x работников, поэтому проверяйте каждый пользовательский класс.

## Что изменило поверхность 2.x

- Модуль EvoUI/Livewire с пятью вкладками.
- Просмотры таблиц/списков, фильтры серверов и модалы детализации только для чтения.
- Адаптивный HTTP-опрос в реальном времени.
- Подавление дублирования для активного идентификатора/действия/нормализованного мета.
- Обновление реестра работников и фильтры классов/титулов.
- Типы расписания: ручной/одноразовый/периодический/обычный/супервайзер.
- Отдельные `SupervisorWorkerInterface`, `SupervisorStatus`, `s_supervisor_states`.
- Аварийная остановка при неудачном переходе на уровне базы данных.
- Компактный интерфейс: приоритет/попытки удалены из текущих столбцов/фильтров.

## До обновления

1. Создать резервную базу данных, `core/composer.lock`, кастомных работников и `storage/stask` аудит по мере необходимости.
2. Фиксировать активные задачи; Пусть закончат.
3. Работники по инвентаризации:

   ```sql
   SELECT id, identifier, class, active, settings FROM s_workers ORDER BY id;
   ```

4. Найдите пользовательские классы, реализующие старый контракт.
5. Проверьте PHP 8.4 и evo-ui 1.2+.

## Работник адаптации

Рекомендуемая форма:

```php
final class ExampleWorker extends BaseWorker
{
    public function identifier(): string { return 'example'; }
    public function scope(): string { return 'custom'; }
    public function icon(): string { return '<i data-lucide="settings"></i>'; }
    public function title(): string { return 'Example'; }
    public function description(): string { return 'Example worker'; }

    public function taskMake(sTaskModel $task, array $options = []): void
    {
        // business logic
        $task->update(['progress' => 100, 'result' => ['ok' => true]]);
        $this->markFinished($task, null, 'Done');
    }
}
```

Посмотрите:

- именование действий `task{StudlyAction}`;
- сигнатуры с опциями `sTaskModel` и массива;
- методы метаданных;
- нет `$modx`; использовать `evo()`/services;
- финализация и путь исключений;
- однострочные сообщения о прогрессе;
- секреты не попадают в интерфейс.

## Расписание миграции

Переместите старые ключи пользовательского расписания на:

```json
{
  "schedule": {
    "enabled": true,
    "type": "periodic",
    "frequency": "hourly",
    "time": "*:10",
    "datetime": "",
    "start_time": "",
    "end_time": ""
  }
}
```

Планировщик 2.x ожидает `taskMake()` для обычных расписаний. Manual/once/periodic/regular — это не cron выражения.

## Миграция супервайзера

Не имитируйте поминутную проверку здоровья, как обычную очередную задачу. Для класса демона добавьте `SupervisorWorkerInterface`, стабильный ключ, проверку только для чтения, отсоединённый старт/перезапуск и благодат. sTask будет создавать строки задач только для событий жизненного цикла.

## База данных

Запустите миграции пакетов и проверьте:

- основные столы не были разрушительной рекреацией;
- `s_supervisor_states` создано;
- разрешение `stask` активно;
- существующие идентификаторы работников не изменялись случайно;
- настройки JSON валиден.

Текущие базовые миграции имеют `Schema::create`, поэтому поведение при безопасной переустановке зависит от текущей верхней ссылки. Всегда обновляйте до проверенного 2.x коммита и запускайте миграционный дым на копии производственной схемы.

## Активы и тайник

```bash
php artisan package:discover
php artisan stask:publish
php artisan cache:clear-full
```

Старый JS/CSS в кэше браузера может нарушать переключение вкладок или живой прогресс.

## Приемный тест

- sTask открывается с помощью роли разрешения;
- каждая из пяти вкладок работает;
- реестр включает таможенных работников;
- ручные `taskMake` концы;
- будущее расписание создаёт задачу в очереди;
- Живой прогресс обновляется с помощью опросов;
- двойной клик открывает модаль;
- экстренная остановка означает, что запись активного тестирования не состоялась;
- Переход состояния супервайзера к стартовому → здоровому без событийного наводнения;
- dDocs показывает локализованное дерево sTask.

## Откат назад

Регулярно откатывайте код/блокировку и базу данных. Не удаляйте `s_supervisor_states` или новые поля, пока процесс 2.x может запускаться. Если 1.x не понимает новые настройки, сохраните резервную копию и подготовьте явное преобразование.
